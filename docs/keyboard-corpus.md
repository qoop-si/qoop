# Keyboard corpus

Gate G1.3. The corpus lives at `crates/qoro-terminal/tests/fixtures/keyboard_corpus.tsv`
and is regenerated by `scripts/keycapture/build-corpus.py`. Every row carries the source
it came from, and the gate refuses a row whose source it does not recognise, so nothing can
be added by hand without saying where it came from.

## Sources

| Source | What it is | Where it was read |
|---|---|---|
| `terminfo:xterm-ghostty` | Ghostty's own terminfo description | `/Applications/Ghostty.app/Contents/Resources/terminfo`, Ghostty 1.3.1 |
| `terminfo:xterm-256color` | the description iTerm2 implements | system ncurses database. iTerm2 3.6.11 ships no entry of its own and sets `TERM` to `xterm-256color` |
| `terminfo:vte-256color` | VTE's description, which is what gnome-terminal is | system ncurses database |
| `ascii` | control codes, which are not per-terminal: a control letter is the letter with bits 6 and 7 cleared (ANSI X3.4) | not a terminal property |
| `xterm-ctlseqs` | the meta prefix, and the cursor keys with cursor key mode off | xterm's ctlseqs |

The terminfo entries were read with `infocmp -x -1`, using ncurses 6.0.20150808.

The f-key numbering above `kf12` and the digit suffix on an extended capability both follow
xterm's modifier parameter table: the parameter is one plus shift 1, alt 2, control 4. That
is the convention the entries are written against, and it is what makes `kf25` mean control
with F1 rather than a twenty fifth physical key.

## Why terminfo is not the whole corpus

terminfo's `kcuu1` and its neighbours are written for application cursor key mode, because
that is the mode a curses application puts the terminal in. A shell sees the other encoding.
A live capture from Ghostty on this machine sent `ESC [ A` for Up and `ESC [ 1 ; 2 A` for
shift with Up, while its own `kcuu1` is `ESC O A`. Both are correct, in different modes, and
a corpus built from terminfo alone would have pinned the decoder to the half a shell never
sends. The `xterm-ctlseqs` rows exist because of that measurement.

## Two byte values that carry two meanings

Neither can be separated on the wire, so the corpus records one side of each and the
decoder's doc comment names the other:

- `0x1b` is Escape and control with `[`. The corpus keeps Escape. A lone `ESC` is only a key
  once the read has settled, which is why `decode` takes `at_idle`.
- `0x08` is control with H, and is also what `xterm-256color` says the Backspace key sends.
  The corpus keeps the control letter and drops that one `kbs` row. Ghostty and VTE both
  send `0x7f` for Backspace, which is unambiguous, so their rows stay.

## Capture

`scripts/keycapture/drive.py` records real key presses from a real emulator: it launches the
emulator running `capture-keys.py` with its stdin in raw mode, drives the key list in
`keys.tsv` through the window server, and writes the bytes that arrived. Rows it produces
enter the corpus with a `capture:` source.

It needs a physically unlocked display, because the window server delivers no synthetic key
events to a locked session and every row comes back empty. It also handles two things that
are otherwise silent corruption: a sentinel keystroke after every key, because several
combinations are taken by the window server before any application sees them (control with
an arrow opens Mission Control) and a positional mapping would shift the whole corpus by
one from the first swallowed key onward; and a readiness handshake, because a fixed sleep is
the difference between a clean run and a corpus whose first rows were typed into a shell.

## Regenerating

```
uv run --no-project python scripts/keycapture/build-corpus.py \
  crates/qoro-terminal/tests/fixtures/keyboard_corpus.tsv
cargo test -p qoro-terminal --test keyboard_corpus
```
